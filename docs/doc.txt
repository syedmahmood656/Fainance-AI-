  2. The Request Flow (Step-by-Step)

  1. User Action: You send a photo of a receipt to the Telegram Bot.
  2. The Hook: Telegram sends that image as a JSON payload to your ngrok URL.
  3. The Entry: ngrok forwards the request to your FastAPI server (/telegram/webhook).
  4. The Processing (LangGraph):
    - Extraction: The code sends the image to the LLM (e.g., GPT-4o or Gemini). The LLM returns a structured list: "Starbucks, $5.50, 2023-10-01".
    - Categorization: A second LLM pass categorizes this as "Food & Dining".
  5. The Storage: The processed data is saved into the Database.
  6. The Response: The bot sends a confirmation message back to you via the Telegram API: "✅ Recorded $5.50 at Starbucks under Food & Dining."

  3. Summary of Problems Solved

  - Manual Entry $\rightarrow$ AI Extraction: You don't have to type in your expenses; the AI does the data entry.
  - Local Dev $\rightarrow$ Public Access: ngrok removes the need to deploy to a cloud server (like AWS or Heroku) just to test the bot.
  - Unstructured $\rightarrow$ Structured: The LLMs transform a random image into a database row that can be used to generate Excel reports.

  #### UPDATE ######

   Since your project is already built on LangGraph, you are in a perfect position to integrate these. LangGraph is
  natively designed for these exact patterns.

  Here are specific ideas for implementing each:

  1. MCP (Model Context Protocol / Tool Calling)

  Instead of having your ExpenseService and ReportService called as hardcoded functions in your nodes, you can turn them
  into Tools.

  - Dynamic Tool Node: Create a ToolNode in LangGraph. Instead of a linear flow (Extract $\rightarrow$ Categorize
    $\rightarrow$ Save), let the LLM decide which tool to call. For example, if a user says "Check my spending and then
    save this receipt," the LLM can call get_report and save_expense in a single turn.
  - External MCP Servers: If you want to expand, you could connect your bot to an MCP server for Google Sheets or
    QuickBooks. Instead of just saving to your local DB, the LLM could "decide" to sync the expense to an external
    accounting tool.
  - Human-in-the-loop (HITL): Use LangGraph's interrupt feature. Before the save_expense tool is executed, the agent
    pauses and sends a "Confirm these details?" message to the user via Telegram. Only upon a "Yes" does the tool
    execute.

  2. LLMOps with LangSmith

  Since you are using LangChain/LangGraph, LangSmith integration is almost zero-config (just environment variables).

  - Tracing & Debugging: Every interaction from Telegram will be traced. You can see exactly where a receipt extraction
    failed—was it the AI's OCR (Extractor) or the logic (Categorizer)?
  - Playground Iteration: When you find a "failed" trace (e.g., the LLM categorized a "Starbucks" coffee as "Office
    Equipment"), you can send that trace to the LangSmith Playground, tweak the prompt, and test it instantly without
    restarting your Docker container.
  - Latency Monitoring: Track how long the extract_receipt node takes. Since Vision models can be slow, you can use
    LangSmith to identify if you need to switch to a faster model for certain tasks.

  3. Evaluation (The "Golden Dataset")

  Evaluation is what separates a "demo" from a "product."

  - Create a "Golden Dataset": Collect 50-100 real-world examples:
    - Input: Receipt Image $\rightarrow$ Expected: Correct Vendor, Amount, Category.
    - Input: "How much did I spend on food in July?" $\rightarrow$ Expected: The correct numeric sum.
  - LLM-as-a-Judge: Write a script that runs your graph against this dataset. Use a more powerful model (like Claude 3.5
    Sonnet or GPT-4o) to compare the Agent's actual output against the "Expected" output and give a score (1-5) based on
    accuracy.
  - Regression Testing: Every time you change your prompt in receipt_extractor.py, run your evaluation suite. This
    ensures that fixing a bug in "Coffee" categorization doesn't accidentally break "Hotel" categorization.
  - A/B Testing: Test two different prompts for ReportParser. Use LangSmith to run both versions against the same 50
    queries and see which one has a higher success rate in parsing dates correctly.
